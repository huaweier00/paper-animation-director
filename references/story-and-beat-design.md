# Story and beat design

## Intake

Resolve or infer the source story, intended lesson, target platform, aspect ratio, target duration, language, subtitle mode, audio mode, and watermark text. Record assumptions in the manifest instead of hiding them in chat history.

Use four approval gates:

1. story action table;
2. voice, character bible, and hardest benchmark scene;
3. complete editable preview;
4. final render and delivery.

## Scene contract

Give every scene:

- one narrative goal;
- one or more observable events;
- one proof frame or proof interval;
- an explicit duration policy;
- a transition reason, not only a transition effect.

Represent each important event as:

```text
cause → action → propagation → result → proof
```

Omit `propagation` only for genuinely instantaneous events. Write `proof` as something a reviewer can observe, not an intention such as “the scene feels cooperative.”

## Pacing policy

- Let measured narration duration set the first timing boundary.
- Introduce new visual information roughly every 1.5–3 seconds.
- Allow a long scene only when it contains multiple internal actions or reactions.
- Start the next voice 0.2–0.6 seconds before the new image fully settles when a J-cut improves continuity.
- Keep normal inter-scene voice gaps around 0.2–0.8 seconds.
- Cut 0.6–1.2 seconds after the scene's final meaningful result unless continuing action or sound earns the hold.
- Do not use slow camera drift, grain, dust, or a breathing texture to justify story duration.

## Action table

Before asset production, make a compact table with scene, goal, cause, action, result, proof, actors, props, and whether a connected ensemble asset is required. Reject any scene whose proof depends entirely on narration.

## Do not overfit one story

Do not assume six scenes, three characters, a temple, water, fire, Chinese setting, or a moral. Preserve the production logic while allowing any number of scenes, actors, settings, and action types.
